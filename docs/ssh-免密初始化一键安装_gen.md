# SSH 免密初始化一键安装方案报告

## 背景

当前项目把 SSH 免密登录视为外部前置条件。安装脚本只负责采集服务器地址、端口、用户名、私钥路径等信息，运行时隧道链路也只支持私钥认证。这导致首次部署时，用户必须先在项目外手动完成以下步骤：

1. 本地生成 SSH 公私钥。
2. 将公钥上传到远端服务器。
3. 验证免密登录可用。
4. 再回到安装流程中填写私钥路径。

这与“一键安装”的目标不一致，也会直接影响连通率，因为当前 SSH 隧道建立依赖公私钥免密认证。

本次方案目标是把这段前置操作自动化，改造成内建能力：首次允许通过服务器用户名和密码登录，自动完成服务专用密钥检测或生成、公钥下发、远端授权配置、免密验证，并将最终运行切换回现有的私钥认证主链路。

## 目标

1. 将 SSH 公私钥检测与自动生成功能集成到一键安装流程。
2. 支持首次通过服务器用户名和密码登录，自动完成公钥下发与免密配置。
3. 安装完成后，服务统一使用服务专用私钥运行，不再依赖当前登录用户目录中的私钥。
4. 在管理端提供“补做免密初始化”入口，用于安装后补救、重试或重新授权。
5. 密码仅在初始化过程内存中使用，绝不写入配置文件、Profile、日志或其他持久介质。
6. 覆盖 Windows、Linux、macOS 三个平台的一键安装能力。
7. 保持现有运行时隧道主链路最小侵入，正式运行仍以私钥认证为主。

## 现状摘要

### 安装侧

现有安装入口是 docs/install，它会分发到：

- Windows: docs/assets/install/install-windows.ps1
- Linux/macOS: docs/assets/install/install-unix.sh

当前安装器只采集已有私钥路径，不会自动生成密钥，也不会执行公钥下发。

### 运行时 SSH 认证

当前 SSH 认证核心在 tunnel/config.go，逻辑是：

1. 读取 ssh.private_key_path。
2. 加载私钥内容。
3. 解析私钥。
4. 使用 ssh.PublicKeys 建立认证。

当前未发现以下能力：

- ssh.Password 密码认证回退
- 初始化期一次性密码登录
- known_hosts 管理
- 公钥自动生成
- authorized_keys 自动写入
- 私钥口令支持

### 配置模型

当前配置与 Profile 只建模了：

- 服务器 IP
- SSH 端口
- 登录用户名
- 私钥路径

没有用于初始化期的非持久密码输入模型，也没有免密初始化状态模型。

### 管理端

配置页已有比较合适的接入位置：

- 视图入口在 views/app_config.gohtml
- 页面处理在 views/handler/admin.go
- API 入口在 api/admin/admin.go

现有页面已经具备弹窗、异步提交、状态轮询模式，适合承载“检测密钥”和“初始化免密”流程。

## 关键设计决策

### 1. 目标范围

本次能力覆盖两类入口：

1. 一键安装脚本
2. 管理端补做入口

原因是首次安装不是唯一场景，实际还需要支持以下情况：

- 远端 authorized_keys 被清空后重新初始化
- 更换服务器后重新授权
- 安装时跳过初始化，后续从管理端补做
- 初始化过程中失败后的再次重试

### 2. 平台范围

覆盖以下平台：

- Windows
- Linux
- macOS

不拆阶段性交付，避免后续不同平台逻辑分叉。

### 3. 密码存储策略

服务器登录密码只允许在初始化流程内存中短暂使用，绝不落盘。

明确禁止写入的位置：

- config.properties
- profiles.json
- viper 持久配置
- 管理端配置更新接口
- 安装日志
- 服务日志

### 4. 服务专用私钥位置

服务最终使用配置目录下的服务专用私钥，不再继续依赖当前用户目录中的私钥。

建议默认路径：

- Windows: C:\ssh-tunnel\.ssh-tunnel\keys\id_ed25519
- Linux: /etc/ssh-tunnel/keys/id_ed25519
- macOS: /etc/ssh-tunnel/keys/id_ed25519

这样做的原因：

1. 路径稳定，适合服务运行。
2. 避免服务依赖当前用户主目录文件。
3. 更符合静态敏感凭据的管理语义。
4. 权限控制更容易统一。

### 5. 默认密钥算法

自动生成时默认使用 ed25519。

原因：

- 用户已确认选择该算法。
- 密钥体积更小。
- 现代 SSH 环境兼容性整体较好。

实现时需要保留兼容提示，处理极少数旧服务器不支持 ed25519 的异常场景。

### 6. 正式运行认证策略

正式运行阶段仍然保持现有私钥认证主链路。

也就是说：

- 初始化阶段新增一次性密码认证能力
- 初始化成功后切换回现有私钥认证模式
- 不把密码认证引入长期运行配置

这是最小侵入方案，也能最大限度复用现有 tunnel/config.go 的认证主路径。

### 7. 管理端接口策略

不复用现有持久化配置更新接口，而是新增独立运行时接口。

原因是现有配置更新链路天然会落盘，不适合承载一次性密码输入。

## 总体方案

本次方案拆成两个层次：

1. 初始化能力层
2. 入口集成层

### 初始化能力层

由 Go 侧新增一套独立的 SSH 初始化逻辑，负责：

1. 检测本地服务专用私钥是否存在。
2. 不存在时自动生成 ed25519 密钥对。
3. 用服务器用户名和密码发起首次 SSH 连接。
4. 在远端创建 ~/.ssh 目录。
5. 修复目录权限。
6. 检查 authorized_keys 是否存在。
7. 幂等写入本地公钥。
8. 修复 authorized_keys 权限。
9. 使用新生成的私钥回连验证免密是否成功。
10. 返回初始化结果与可读状态。

初始化成功后，最终只保留私钥路径作为长期运行配置。

### 入口集成层

#### 安装脚本侧

安装器不再要求用户先准备现有私钥路径，而是改成：

1. 收集服务器地址、SSH 端口、登录用户名。
2. 询问一次性登录密码。
3. 确定服务专用私钥目标路径。
4. 检测目标路径下是否已存在密钥。
5. 不存在则自动生成。
6. 执行免密初始化。
7. 成功后写入最终配置并安装服务。

#### 管理端侧

在配置页补充两类能力：

1. 检测密钥状态
2. 初始化或重建免密授权

页面允许用户输入一次性密码，但该密码只用于本次请求执行，不进入持久配置。

## 详细设计

## 一、服务专用私钥策略

### 路径规则

统一在配置目录下新增 keys 子目录：

- Windows: C:\ssh-tunnel\.ssh-tunnel\keys
- Linux: /etc/ssh-tunnel/keys
- macOS: /etc/ssh-tunnel/keys

默认文件名：

- 私钥: id_ed25519
- 公钥: id_ed25519.pub

### 权限要求

本地权限建议：

- 私钥文件仅服务运行用户可读
- 公钥文件可普通读取
- keys 目录限制访问范围

Linux/macOS 至少保证：

- keys 目录 0700
- 私钥文件 0600
- 公钥文件 0644

Windows 使用服务目录下的最小访问控制策略，确保服务可读且不对普通用户开放不必要权限。

## 二、初始化认证链路

### 初始化阶段认证方式

新增仅用于初始化的一次性认证逻辑：

1. 用户输入服务器用户名和密码。
2. 系统用 ssh.Password 建立首次连接。
3. 在远端执行授权准备。
4. 公钥写入完成后，用私钥重新连接验证。
5. 验证通过后结束初始化。

### 正式运行阶段认证方式

保持现有模式：

1. 从配置读取 ssh.private_key_path。
2. 加载私钥。
3. 使用私钥认证建立隧道。

这样能确保运行期逻辑仍然集中在当前私钥认证主链路上。

## 三、远端 authorized_keys 下发策略

### 远端动作

初始化逻辑需要在远端通过 SSH 会话执行以下动作：

1. mkdir -p ~/.ssh
2. chmod 700 ~/.ssh
3. touch ~/.ssh/authorized_keys
4. chmod 600 ~/.ssh/authorized_keys
5. 检查目标公钥是否已存在
6. 不存在则追加

### 幂等要求

必须保证重复执行不会产生重复公钥条目。

建议策略：

1. 先读取或 grep 检查公钥是否已存在。
2. 仅在不存在时追加。
3. 追加时保留明确 comment，便于后续识别。

### 权限修复

无论远端文件原始状态如何，每次初始化都应补做权限修复：

- ~/.ssh 为 700
- authorized_keys 为 600

## 四、管理端接入设计

### 页面入口

优先放在配置页，而不是版本页。

原因：

1. 配置页天然承载 SSH 目标、用户和私钥路径。
2. 现有页面已有表单、弹窗和异步交互模式。
3. 语义上更符合“连接配置初始化”。

建议新增入口：

1. 检测密钥状态
2. 初始化免密
3. 重新下发公钥

### 管理端接口

建议新增三类接口：

1. 检测接口
2. 初始化执行接口
3. 状态查询接口

其中：

- 检测接口负责返回本地密钥存在性、路径、是否建议重新初始化等信息。
- 初始化执行接口接收一次性密码与必要上下文，立即执行，不持久化密码。
- 状态查询接口返回当前任务进度、结果、错误信息。

### 一次性密码输入模型

密码不进入配置模型，不进入 Profile 模型，只作为独立请求体字段出现。

请求体最小字段建议包括：

- serverIp
- serverSshPort
- loginUser
- password
- targetPrivateKeyPath
- regenerateIfMissing

如果页面已有活动 Profile，可只传 password 和少量覆盖参数，其余从当前配置或当前 Profile 读取。

## 五、安装脚本集成设计

### Windows 安装器

当前 PowerShell 安装器需要从“用户输入现有私钥路径”切换为：

1. 确认服务目录与配置目录。
2. 默认生成服务专用私钥目标路径。
3. 询问服务器密码。
4. 调用初始化能力完成授权。
5. 成功后写入配置文件。
6. 安装或重启服务。

### Unix 安装器

Linux/macOS 安装器按同样思路改造：

1. 默认使用 /etc/ssh-tunnel/keys/id_ed25519。
2. 采集一次性服务器密码。
3. 调用初始化能力。
4. 写入最终配置并完成服务安装。

### 安装器与 Go 逻辑复用

应尽量复用 Go 侧初始化能力，避免在 PowerShell 和 Shell 中分别维护远端 authorized_keys 操作细节。

理想方式是：

1. 安装器负责采集输入。
2. 初始化核心逻辑由程序本体执行。
3. 安装器只消费结果并继续完成服务注册。

这样可以避免三端脚本各自实现 SSH 会话、公钥拼接、远端权限修复和失败处理。

## 六、状态模型设计

### 状态类型

需要新增仅在运行时存在的初始化状态模型，至少覆盖：

- 未检测
- 无本地密钥
- 已有本地密钥但未验证远端授权
- 初始化中
- 初始化成功
- 初始化失败

### 状态用途

用于：

1. 管理端轮询展示
2. 初始化过程提示
3. 失败原因回显
4. 判断是否需要再次执行授权

### 非持久化原则

该状态仅保存在内存中，不进入配置文件，不进入 profiles.json。

## 七、安全边界

### 密码

必须满足以下要求：

1. 不写日志。
2. 不写配置。
3. 不写 Profile。
4. 不进入错误消息原文拼接。
5. 请求结束后不继续持有引用。

### 私钥

必须满足以下要求：

1. 使用服务专用路径。
2. 严格控制本地文件权限。
3. 不在日志中打印内容。
4. 不通过管理端接口直接回显。

### 主机校验

当前运行时仍使用 InsecureIgnoreHostKey，这意味着首次密码登录初始化存在中间人风险。

这是本方案保留的已知风险之一。若后续提高安全等级，可在下一阶段补做：

1. 首次展示指纹确认
2. 持久化 known_hosts
3. 运行时启用 host key 校验

本次方案不把这一块纳入主目标，以避免改动面过大。

## 验证方案

### 功能验证

1. 全新环境下，本地无服务专用密钥时能自动生成密钥。
2. 首次通过密码登录能成功完成公钥下发。
3. 初始化完成后可用私钥免密登录。
4. 服务启动后能够正常建立隧道。

### 幂等验证

1. 多次执行初始化不会重复写入 authorized_keys。
2. 已存在本地密钥时不会重复生成。
3. 已完成授权时再次执行仍然安全。

### 安全验证

1. 密码不落盘。
2. 密码不出现在日志。
3. 私钥权限符合预期。
4. 管理端页面不会回显密码。

### 平台验证

1. Windows 安装流程验证通过。
2. Linux 安装流程验证通过。
3. macOS 安装流程验证通过。

### 构建与回归

建议执行：

1. go build -o ssh-tunnel.exe .
2. go test -v ./...

并结合实际服务启动与管理端页面做手工验证。

## 已知风险与边界

1. 当前 host key 校验仍然不安全，首次初始化存在中间人风险。
2. ed25519 在极老旧 SSH 服务端上可能不兼容，需要明确错误提示。
3. 如果管理端被配置为对外监听，提交一次性密码会扩大暴露面，因此应优先约束管理端监听范围。
4. 服务专用私钥的 Windows ACL 处理需要仔细实现，避免默认权限过宽。
5. 初始化失败后的回滚策略需要明确，至少要保证不会因为失败而留下错误配置。

## 结论

这次改造的核心不是简单修改安装脚本，而是把“SSH 免密初始化”升级为系统内建能力。推荐方案是：

1. 以 Go 侧新增初始化能力为核心。
2. 安装器与管理端都复用该能力。
3. 初始化阶段允许一次性密码登录。
4. 正式运行阶段继续回归现有私钥认证主链路。
5. 服务专用私钥统一落在配置目录下。
6. 密码严格内存态处理，不参与持久化。

该方案既满足一键自动化目标，也能在不大幅破坏现有架构的前提下完成落地。
